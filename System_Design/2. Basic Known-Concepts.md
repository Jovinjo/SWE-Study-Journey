### 1.6. HTTP/HTTPS

<img width="384" height="601" alt="image" src="https://github.com/user-attachments/assets/06e47351-a73b-43b6-beca-08e839c496c7" />

## Concept 2. API - How application exchange data / How data move around

### 2.1. API 

<img width="796" height="140" alt="image" src="https://github.com/user-attachments/assets/ba80a8fc-a5c7-4e54-8d2a-c6cf13a6bd3f" />

API allows us to define what data you can request, how to define it, how the response look like. It mostly use JSON format over HTTP protocol <br />
Two types: REST and GraphQL

#### 2.1.1. REST API

<img width="796" height="185" alt="image" src="https://github.com/user-attachments/assets/1175935f-42e5-4a1e-acab-3a6a02b100d9" />

Key principles: stateless (no session on server), cacheable (responses can be cached), consistent uniform URL <br />
Problem: If client needs data from multiple sources, then it needs multiple request.

#### 2.1.2. GraphQL

<img width="785" height="405" alt="image" src="https://github.com/user-attachments/assets/32ec3ee5-f9e2-4812-bdd1-daca8b9fd851" />

Key principles: combine multiple request to one and get combined results (e.g. /users/123 and /users/123/comment) <br />
Problem: complexity on server side when too many nested data, can make caching harder.

### 2.2. WebSockets

<img width="335" height="604" alt="image" src="https://github.com/user-attachments/assets/9086e972-9c8b-496d-8f2a-e04f24564ac4" />

HTTP sends one-way request, where client needs to initiate first. What about when server needs to send to client first? e.g. live score updates, chat apps notifications. <br />

Benefit: Once it established it can send message without any HTTP request which is perfect for real-time features. <br />
Problem: It is stateful which mean it saves the conversation / sessions. If server down, then all the conversation lost

### 2.3. Webhooks

What happens when server needs to notify another server (e.g. third-party platform)? <br />
Example:<br />
- when user make payment in amazon using paypal, paypal needs to send notifications immediately.
- when user push code to github, third-party CI/CD system need to be triggered

<img width="392" height="715" alt="image" src="https://github.com/user-attachments/assets/1bd6f04e-e2f5-4778-b16e-815c9a4092f3" />

The key challenge: What if your server is down when the webhook fires? <br />
Good webhook systems´: include retry logic, event logging, and idempotency handling.

## Concept 3. Data Storage

### 3.1. Database

1. Relational Database (PostgreSQL, MySQL): structured tables with relationship (e.g. transaction data)
2. Document Database / Non-relational (MongoDB): store data as flexible JSON documents
3. Key-value Database (Redis, DynamoDB): like hash maps and using key for look up database
4. Graph Database (Neo4j): ideal for social networks or recommendations engines.

How to choose: based on data model, query patterns, and scalability requirements

### 3.2. SQL vs NoSQL

<img width="738" height="100" alt="image" src="https://github.com/user-attachments/assets/f585bc10-447b-4791-bc72-0dce4ddfe2e0" />

Choose SQL when: need strong consistency (e.g. banking, inventory), complex queries relations with joins, schemas that not often changed, and ACID transactions. 

<img width="737" height="99" alt="image" src="https://github.com/user-attachments/assets/b44d7370-556f-4481-a554-f90076611616" />

Choose NoSQL when: schema evolve frequently, save or process large amount of data, data is unstructured (e.g. logs, social media post)

### 3.3. Database Indexing - Help to find data quickly

Most databases use B-tree indexes by default > support O(log n) lookups.

Trade-off: Indexes speed up READ but slow down WRITE, because every INSERT needs to update the index. <br />
Trick: Index columns that appear in WHERE and JOIN.

### 3.4. Vertical Partitioning

What happens when single database can not hold all your data? Do vertical partitioning.

<img width="793" height="387" alt="image" src="https://github.com/user-attachments/assets/139bf4ce-b483-42d5-a246-290f393589eb" />

Idea: seperate data into subset of table and connected by a shared key (e.g. ID)
Benefit: <br />
- Query only touches the columns that it actually needs - fewer bytes read from disk and faster response
- Improve security (query asking for billing can have stricter access controls)
- Optimization can be done independently for each table

### 3.5. Caching

<img width="787" height="276" alt="image" src="https://github.com/user-attachments/assets/b11fd64b-303b-496a-adc4-15c88f636bd7" />

Caching allows to accessed data in faster layer than database (usually memory) > improve READ performance

Common one like above is cache-aside (or lazy loading). REDIS and Memcached are the most popular used in-memory caches.

Challenge: INVALIDATION - when database updated, the cache needs to be updated/cleared too. <br />
Tricks: TTL (time-to-live where data expires automatically), write-through (update cache and database together), and write-behind (update cache first, database later)

### 3.6. Denormalization

Caching helps with READ performance. What about if Query need to join multiple tables?

<img width="766" height="319" alt="image" src="https://github.com/user-attachments/assets/68e0339e-ad2b-42d3-a28c-6e77dbd3ca21" />

In normalized table - order is seperated from user and product table > problem: multiple JOINS needed.<br />
In denormalized table - you add the column from user and product table to the order table for faster read despite of redundancy.

Problem: If user name changed, then multiple table need to be updated.<br />
Trick: find strategy to keep redundant data consistent by update, use this when system is read-heavy and involve expensive joins.
