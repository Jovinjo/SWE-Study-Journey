## Concept 3. Data Storage - Where data lives

### 3.1. Database

1. Relational Database (PostgreSQL, MySQL): structured tables with relationship (e.g. transaction data)
2. Document Database / Non-relational (MongoDB): store data as flexible JSON documents
3. Key-value Database (Redis, DynamoDB): like hash maps and using key for look up database
4. Graph Database (Neo4j): ideal for social networks or recommendations engines.

How to choose: based on data model, query patterns, and scalability requirements

### 3.2. SQL vs NoSQL

<img width="738" height="100" alt="image" src="https://github.com/user-attachments/assets/f585bc10-447b-4791-bc72-0dce4ddfe2e0" />

Choose SQL when: need strong consistency (e.g. banking, inventory), complex queries relations with joins, schemas that not often changed, and ACID transactions. 

<img width="737" height="99" alt="image" src="https://github.com/user-attachments/assets/b44d7370-556f-4481-a554-f90076611616" />

Choose NoSQL when: schema evolve frequently, save or process large amount of data, data is unstructured (e.g. logs, social media post)

### 3.3. Database Indexing - Help to find data quickly

Most databases use B-tree indexes by default > support O(log n) lookups.

Trade-off: Indexes speed up READ but slow down WRITE, because every INSERT needs to update the index. <br />
Trick: Index columns that appear in WHERE and JOIN.

### 3.4. Vertical Partitioning

What happens when single database can not hold all your data? Do vertical partitioning.

<img width="793" height="387" alt="image" src="https://github.com/user-attachments/assets/139bf4ce-b483-42d5-a246-290f393589eb" />

Idea: seperate data into subset of table and connected by a shared key (e.g. ID)
Benefit: <br />
- Query only touches the columns that it actually needs - fewer bytes read from disk and faster response
- Improve security (query asking for billing can have stricter access controls)
- Optimization can be done independently for each table

### 3.5. Caching

<img width="787" height="276" alt="image" src="https://github.com/user-attachments/assets/b11fd64b-303b-496a-adc4-15c88f636bd7" />

Caching allows to accessed data in faster layer than database (usually memory) > improve READ performance

Common one like above is cache-aside (or lazy loading). REDIS and Memcached are the most popular used in-memory caches.

Challenge: INVALIDATION - when database updated, the cache needs to be updated/cleared too. <br />
Tricks: TTL (time-to-live where data expires automatically), write-through (update cache and database together), and write-behind (update cache first, database later)

### 3.6. Denormalization

Caching helps with READ performance. What about if Query need to join multiple tables?

<img width="766" height="319" alt="image" src="https://github.com/user-attachments/assets/68e0339e-ad2b-42d3-a28c-6e77dbd3ca21" />

In normalized table - order is seperated from user and product table > problem: multiple JOINS needed.<br />
In denormalized table - you add the column from user and product table to the order table for faster read despite of redundancy.

Problem: If user name changed, then multiple table need to be updated.<br />
Trick: find strategy to keep redundant data consistent by update, use this when system is read-heavy and involve expensive joins.

### 3.7. Blob Storage

BLOB (Binary Large Objects) are necessary for large data like images, videos, and PDFs. <br />
Example: Amazon S3, Google CLoud, Azure Cloud.

## Concept 4. Scaling - More traffic, more data, more users, what now?

### 4.1. Vertical Scaling (Scale Up)

<img width="790" height="101" alt="image" src="https://github.com/user-attachments/assets/7c4b1f0c-d7c6-4ef2-aef8-c3a968c13e46" />

More CPU, More RAM! <br />
Problem: Largest cloud instance is 64 CPU and 256GB RAM and cant be scaled further, If one big server goes down then everything going down.

### 4.2. Horizontal Scaling (Scale Out)

<img width="787" height="392" alt="image" src="https://github.com/user-attachments/assets/2873a4f3-694c-4060-bd2d-b91772d90fa9" />

Add more server! <br />
This is what large-scale company works like Google, Netflix, Amazon with thousands of servers.

Problem is adding complexity: <br />
  - Server need to be stateless
  - Session data needs to be in a shared storage (like Cache Redis) and not in server memory.
  - Need a load balancer (control which server handles which request)
  - Need a scaling strategy (replication, sharding)

### 4.3. Load Balancers

<img width="750" height="430" alt="image" src="https://github.com/user-attachments/assets/85ce7e3f-ee07-4744-a95f-4c7e0bbc4e07" />

How to know which server handles which request? common methods are: <br />
1. Round Robin - requests go to servers in order
2. Least connections - send to server that has fewest requests
3. Weighted - servers with more capacity get more traffic

Benefit: Scalability (distribute load to many servers), Availability (If one server stop, automatically route request to healthy server.

Hint: Load balancer can be used for web server (frontend), application server (backend), or for databases

### 4.4. Replication (READ Scaling)

Replication allows to copy primary database to multiple database servers.

Common one is: PRIMARY-Replica (All WRITE goes to Primary DB > changes replicated to one or more replica > READ only from replica servers)

<img width="731" height="382" alt="image" src="https://github.com/user-attachments/assets/b14ae42a-7081-42fd-9de9-c0e68fd5f3a3" />

Example: App like Twitter/X where READ-heavy and WRITE-heavy. <br /> <br />
Benefit: Reduce load in primary DB, can handle more READ-traffic, if replica fails then reads are redirected to other replicas, if primary fails then replica can be promoted to take over. <br /> <br />
Problem: replication lag (small delay between when data is WRITTEn to primary and when it can be READ in replica, e.g. your instagram post that appears later on other people's)

### 4.5. Sharding (WRITE Scaling)

Sharding allows to split data in multiple database nodes > each nodes hold different subset (portion) of the data. A shard_key is used to determine which shard/nodes holds the portion of the data.

<img width="414" height="411" alt="image" src="https://github.com/user-attachments/assets/8eaa9cb0-c3bf-47f8-a0be-2cc1c8a39504" />

Common Approach: <br />
1. HASH-based Sharding - Compute a hash of the key (e.g. user_id) and use modulo to pick a shard key
2. Range-based Sharding - use consecutive key ranges to each shard key.

Challanges: Cross-shard queries (join data across shards is expensive), rebalancing (add a new shard means redistributing data again), and complexity operation.

## Concept 5. Distributed Systems - What to do when we run multiple systems (e.g. Servers, databases, caches)?

When multiple servers or databases already comes to play, the system turns to category of "Distributed System" and not single machine anymore. Data Consistency is one challenge, another is also delivering fast response to the users.

### 5.1. CAP Theorem

<img width="798" height="380" alt="image" src="https://github.com/user-attachments/assets/22d9e6b4-30dd-489b-b8a8-ff91f0d0e4b0" />

- Consistency - every read returns the latest write
- Availability - every request gets a response
- Partition Tolerance - System works even if links between nodes/join fails

However, Partition Tolerance need always to be there and can not be escaped. Therefore there are 2 choices: <br />
1. CP (Consistency + Partition) <br />
    - Example: MongoDB, HBase <br />
    - Feature: Refuse request if they cant guarantee up-to-date data. <br />
    - Use case: better for banking, inventory. <br />
2. AP (Availability + Partition) <br />
    - Example: Cassandra, DynamoDB <br />
    - Feature: Always respond even if data is appeared delayed <br />
    - Use case: better for social media feeds, product catalogs, or analytics where avaialability matters than accuracy

### 5.2. CDN (Content Devlivery Network)

<img width="586" height="551" alt="image" src="https://github.com/user-attachments/assets/fa3d7474-0272-40bb-a9cf-13630319bade" />

CDN is network of servers that distributed across the globe. It allows to caches and serves content from location server close to users.

What does it serve primarily > Static content like images, CSS, JS, videos. 

Example of CDN providers: CloudFront (AWS), CloudFlare (allows also to cache dynamic content or running serverless functions at the edge - executing lightweight code), Akamai.

Benefit: Reduce latency, decrease load on the central server, and improve availability (cached content still can be served)

### 5.3. Idempotency

In distributed systems, request can fail and then be retried again by users (e.g. a network time out where server already process the request but the response got lost). This is dangerous, e.g. in payment, where client retries and ending up charging customer twice or sending duplciate emails.

<img width="427" height="607" alt="image" src="https://github.com/user-attachments/assets/7e27713d-ab95-449a-8987-2f692e4fe309" />

Solution: IDEMPOTENCY operation

What is it: produce the same result regardless of how many times you execute it. Some HTTP operation already naturally idempotent, but some need idempotency key.

Example:
  - GET - getting resource twice returns the same thing > Idempotent
  - DELETE - deleting already-deleted content is nothing happen > Idempotent
  - POST - Not Idempotent > thus need "idempotency key" which is a unique identifier everytime the client sends request. The server will check if it has already processed the request with that key and returns the cached result instead of processing again.

Use Case: Stripe, Paypal, and most payment API, or order creation, or operation where duplicates processing request can be harmful.

## Concept 6. Architecture Patterns - How to organize large scale system?

From networking to storage and to scaling. How do we organize all these into a coherent system > Architecture Patterns!

### 6.1. Microservices

Problem: When application grow, a MONOLITH (single codebase) can be hard to be maintained 

Solution: MICROSERVICES > split application into small and independent services with its own DB. Each is developed, deployed, and scaled independenlty. Different teams can manage different services

<img width="789" height="259" alt="image" src="https://github.com/user-attachments/assets/d348f33e-a3b3-4c8e-a9de-aef804c44d4c" />

Example: 
- Payment service handling too much traffic > just do scaling on that service
- A bug in inventory service > fix and deploy without touching other service

Challenge:
- Distributed system complexity (network calls instead of function calls)
- Data inconsistency (no easy JOIN)
- Operational Complexity (monitoring, deploying, and debugging)

### 6.2. Synchronous vs Asynchronous Communication (Message Queues)

<img width="790" height="331" alt="image" src="https://github.com/user-attachments/assets/cefecbaa-b34f-4acb-bcf2-de1142471822" />

Synchronous communication:
- Service A calls service B and waits for response
- If service B slow down, service A suffers

Asynchronous communication:
- decouple services by introducing an intermediary that stores messages until the consumer ready to process
- When user place an order, the order service does not wait for the email to be sent, inventory to be updated, analytics to be recorded. It drops the message on the "Message Queue" and move on the next user. If the email service is down for a minute, the messages wait in the queue and get processed when it comes back.

Benefit of using Message Queue Tools (e.g. Kafka, RabbitMQ, SQS from AWS):
    - Decoupling - services do not need to know about each other
    - Buffering - handle traffic
    - Reliability - messages persist even if consumer crash
    - Scalability - faster process

Question: Services are decoupled now, but every external client still needs to know the address of every service. How do you simplify that?

### 6.3. Rate Limiting API

In order to protect the API request from being overwhelmed, you need to control RATE Limit (how many requests client can make within time window). It prevents abuse of backend service and ensure fair usage.

<img width="795" height="251" alt="image" src="https://github.com/user-attachments/assets/6bf029fc-83c5-4437-8633-7e32dbc96b30" />

Common Algorithm:
    1. Token Bucket - Token refill at a fixed rate. Each request cost a token
    2. Sliding Window - Count requests in a time window
    3. Fixed Window - Count request in discrete time interval

How it works: Rate limiter usually sits at the API Gateway level and use a fast store db like Redis to track request counts per client.

Benefit of Rate Limiting:
- Preventing DDoS attacks (try to crash service)
- Protecting expensive operations (e.g. database queries)
- Enforcing API usage benefit (paid users get 10,000 requests)

### 6.4. API Gateway

How do you manage all of them, authentication, routing, rate limiting, without duplicating logic across every service? API GATEWAY!

Instead of user talking to dozens of micro services, they talk to gateway. Examples are Kong, AWS API Gateway, Nginx.

<img width="780" height="416" alt="image" src="https://github.com/user-attachments/assets/8f9debb3-fa80-4989-b214-696f32286f6e" />

Benefit:
- Instead of client needs to know addresses of 20 services, the client only knows on URL.
- Gateway routes each request to the right service.

Variation of Gateway capabilites:
1. Request/response transformation - converting between protocols or data formats
2. Response aggregation - combine results from multiple services into one response
3. Caching
4. Circuit breaking - stopping requests to a failing service
